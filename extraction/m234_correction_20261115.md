### 3.1 Cause: the numexpr fault, not the 09:05 code edit

The earlier note (`m1_correction_20261115.md` §8) attributed the three shifts to edits of `tools/m23_common_i139.py` at 09:05, after M2 ran (08:37 to 08:39). The evidence says otherwise.

1. **The code before 09:05 already gave the new n.** M3 ran at 08:3x with the same `m23_common_i139.py` as M2, before the 09:05 edit. Its `n_paper_sample` (builder domain, complete on y and the paper's terms, correct weight > 0) is the same sample that M2 regime (i) fits (`nhanes_core.svy_logit` takes complete cases in the domain with weight > 0). The recorded M3 values are 8641, 37018 and 5528 (`extraction/m3_pre-numexpr-fix_20261115/<rec_id>.json`), equal to the new M2 regime (i) n, not to the recorded 7900, 37361 and 5623. So the recorded M2 n did not come from the code version of that time either.
2. **One lost file reproduces the recorded rows exactly.** `tools/m2_fileloss_sim_i139.py` loads each paper with the fixed code, then, one file at a time, replaces every cached XPT file above 1e6 numeric cells by the all-zero frame that the fault produces (SEQN 0) and recomputes n for regimes (i), (ii) and (iii). For all three papers the only file that reproduces all recorded n is the same one: `2003-2004/MCQ_C.xpt` as cached by `m1_lib_i139._read` (logs `extraction/m2_fileloss_sim_6b7f67827b.txt`, `..._94132d0c1a.txt`, `..._a906145f51.txt`; 6b7f67827b 7900 / 8365 / 8365, 94132d0c1a 37361, a906145f51 5623).
3. **It hits exactly these three papers.** M2 runs all papers in one process in M1 table order, so a bad cached copy stays for every later paper. Of the 15 papers of the original M2 run, only these three read MCQ through `lib.raw` and include 2003-2004 (6b7f67827b heart failure MCQ160B as a covariate; 94132d0c1a cancer MCQ220 as an exclusion; a906145f51 liver MCQ160L and cancer MCQ220 as exclusions). The other papers either do not read MCQ through `lib.raw` or do not include 2003-2004, and their rows are unchanged.
4. **The direction fits.** A covariate that becomes missing for a cycle removes those people under complete case (6b7f67827b: n smaller). An exclusion coded "missing kept" stops excluding anyone in that cycle (94132d0c1a, a906145f51: n larger). An edit to the weight or sample rule would not produce n moving in opposite directions in this pattern.

No copy of the 08:37 source exists (its sha256 in `m2_m3_rules_i139.sha256`, `473a4f5a…`, differs from today's `cc6449d3…`). The current file reads the weight threshold from `I139_W_THRESHOLD` (default 0.80) and `m3_run_i139.py` reads its output folder from `I139_M3_OUT`; both are used by the 99 % threshold sensitivity run of 09:09 to 09:11, which is the likely purpose of the 09:05 edit. Whatever the edit was, point 1 shows that it did not change the samples of these papers. The new rows are the correct ones under the locked rules (amendment 1, threshold 80 %).
